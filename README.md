# Wisp

Wisp is a modern browser extension built to help you organize, protect, and maintain your bookmarks with less hassle. It detects broken links, finds duplicates, manages private saved content, and lets you browse bookmarks in a cleaner, more structured way.

Built with TypeScript and React on top of the Plasmo framework, Wisp is designed for users who want a smarter bookmark experience — without the clutter.

## Why Wisp?

Most bookmark managers feel like they haven't changed since 2010. They're slow to search, hard to organize, and give you no insight into what's actually inside your bookmark collection. Wisp was built to fix that.

### What Wisp does better

- **It tells you what's broken.** Wisp actively health-checks your links and surfaces dead or unverifiable URLs — so you're not the one who discovers a 404 six months after saving it.
- **It cleans up after you.** Duplicate detection finds near-identical bookmarks (same URL, same content, different titles) and lets you remove them in bulk instead of one painful click at a time.
- **It forgets the right things.** Forgotten-bookmark tracking surfaces links you haven't opened in months or years, so you can prune or rediscover them on your terms.
- **It keeps secrets actually secret.** A password-protected private vault hides sensitive bookmarks from the main tree, with real encryption at rest (see [Private Vault](#private-vault) below).
- **It's fast and structured.** Timeline and category-based browsing, instant search, and group-by-domain/month/topic modes make large collections navigable instead of overwhelming.
- **It looks like a modern app.** Light and dark themes, a clean extension UI, and thoughtful micro-interactions — not a browser-styled list.
- **It's cross-browser from day one.** A single `browserApi` abstraction wraps `chrome.*` and `browser.*` so the same extension code behaves correctly on Chrome, Edge, and Firefox.
- **It recovers when things go wrong.** Wisp backup/restore and standard HTML bookmark import/export are built in, plus bug-reporting tools and system diagnostics so issues get fixed instead of ignored.

If a bookmark manager's job is to help you *keep* bookmarks, Wisp's job is to help you *keep the right ones*.

- Smart bookmark organization (topic, domain, month, and date grouping)

## Private Vault

Wisp's private vault hides sensitive bookmarks from the main tree and encrypts them at rest, so a casual glance at `storage.local` (or a synced profile) does not reveal your private links.

**How it works:**

- **Encryption standard: AES-GCM 256-bit**, performed with the browser's native [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API) — no third-party crypto libraries.
- **Key derivation:** your vault password is stretched into a 256-bit AES key using **PBKDF2 with SHA-256** and a high iteration count, combined with a per-vault **cryptographically random salt** generated by `crypto.getRandomValues`.
- **Per-entry encryption:** each vault entry is encrypted with a **unique random IV** (initialization vector), preventing pattern leakage between entries. The IV is stored alongside the ciphertext and is not secret.
- **Authentication:** AES-GCM is an authenticated cipher — tampered ciphertext fails to decrypt, so corrupted or forged vault data is rejected rather than silently returned as garbage.
- **In-memory session only:** the decrypted vault is held in memory while unlocked and is **never written to disk in plaintext**. Locking the vault (or the auto-lock alarm firing) discards the key and the decrypted contents.
- **Auto-lock:** an `alarms`-based timer (`browserApi.alarms`) automatically re-locks the vault after inactivity, so walking away from your machine doesn't leave it open.
- **Passwords are never stored.** Wisp stores only the salt and a verification blob needed to confirm the correct password on unlock — the password itself is not persisted anywhere.

If you lose your vault password, the encrypted entries cannot be recovered. That's by design.

## Favicons

Wisp fetches site favicons through **Google's public favicon service** (`https://www.google.com/s2/favicons`). This gives us:

- consistent favicons for sites that don't expose a `/favicon.ico` at the root
- no extra host permissions needed beyond what the extension already requests
- browser-level caching so the same icon isn't fetched twice
- a graceful default icon for sites Google can't resolve

No user data is sent — the request is a plain HTTPS GET keyed by the site's hostname.

## Getting Started

### Prerequisites

- Node.js 18+
- npm

### Installation

```bash
git clone https://github.com/LakshanWC/Wisp.git
cd Wisp
npm install
```

## Development

Run the extension in development mode:

```bash
npm run dev
```

This starts the Plasmo development environment so you can test the extension in your browser.

## Production Build

```bash
npm run build
```

This generates the packaged extension files for deployment or local testing.

## Loading the Extension

1. Open your browser's extension page
2. Enable Developer Mode
3. Click **Load unpacked**
4. Select the generated build folder
5. Start using Wisp

## Permissions

Wisp requests the following browser permissions:

| Permission | Why it's needed |
|---|---|
| `bookmarks` | Read, create, update, and delete bookmarks |
| `storage` | Persist metadata, visits, health checks, and the vault |
| `unlimitedStorage` | Allow large bookmark collections without quota errors |
| `alarms` | Vault auto-lock timer and scheduled maintenance |
| `http://*/*` and `https://*/*` | Required to send health-check requests to arbitrary saved URLs so Wisp can determine whether a link is alive, dead, or unverifiable |

### A note on host permissions

- `http://*/*` and `https://*/*` are **broad host permissions** — they let the extension issue requests to any HTTP/HTTPS URL. They're what make dead-link detection possible, since Wisp can't know in advance which URLs a user will save.
- Health checks are designed to avoid downloads and side effects by using:
  - **`HEAD`** rather than `GET` — `HEAD` requests response headers only, so the intent is that the body of a linked file (a `.zip`, `.pdf`, video, installer, etc.) is not fetched.
  - **`mode: "no-cors"`** — the request is treated as an opaque cross-origin probe rather than a normal navigation, so it isn't expected to trigger the browser's download prompt or be cached under your session.
  - **`credentials: "omit"`** — no cookies or session credentials are sent with the probe.
  - A short **`AbortController` timeout** — hangs and dead hosts are cut off quickly.
- These measures are intended to make health checks harmless to your bookmark targets. They are a best-effort design, not a formal guarantee: unusual server behavior, redirect chains, or changes to browser fetch semantics could in principle produce an unexpected result. If you notice one, please open an issue .
